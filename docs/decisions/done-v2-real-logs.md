# done v2: a real-log hold-out with re-defined metrics

Registered 2026-10-02 before any case is fetched, labelled, parsed or sent to Jev; the commit that first contains this file is the registration. One thing was looked at first, only to learn the log format: the job list and job log of one `BurntSushi/ripgrep` run (no case was drawn from it; that repository is excluded from the sample).

## Why, and what this is not

Six registered hold-outs of `done` v2 ([fifth](done-v2-holdout5.md), [sixth](done-v2-holdout6.md) and earlier) were written by agents from memory of tool formats. Each one picked tools that have no parser and so measured the tail again. The registered bar also contradicts a safety rule: it asks for `met` in at least 60% of expected-`met` cases of any tool, while `done` never says `met` for output it cannot read. A seventh invented hold-out would produce no information.

**This is a re-definition of the success bar, made after six failed registered checks.** The old bar is not met and is not replaced: `done` v2 stays "not measured" on the old bar whatever happens here. The new metrics measure something narrower and different, stated below, on real logs nobody wrote for this test.

## Metrics (fixed now)

Unit: one case = one test, lint or build step of one real GitHub Actions job.

1. **Wrong `met`: 0 (hard bar).** Over cases whose expected label is `missing` and whose step succeeded (so Jev was asked), the number of `met` verdicts. Reported with n and the exact one-sided 95% upper bound (Clopper-Pearson; for 0 of n it is 1 - 0.05^(1/n)). Counted separately for the `parsed` and the `exit_code` trust bucket and in total; the bar applies to the total, so a wrong `met` in the exit-code bucket (the failure of the sixth hold-out) fails it.
2. **Parsed coverage.** Of kept success-step cases, the share whose evidence a parser recognises (`parseEvidence(...).trust` is `parsed`, i.e. at least one runner fact; the appended exit line does not affect it). Exact 95% two-sided interval; also by criterion and by language. No bar; it is a measurement of what the parsers reach on real logs.
3. **`met` recall among parsed.** Over cases that are expected `met` and parsed: share with verdict `met`. **Bar 0.9, evaluated only if at least 30 such cases exist**; with fewer it is reported as "not evaluable (n = k)" with the point value and interval, and no verdict. Cases that are not parsed are never counted against recall: a log with no recognised runner is `unsure` by design. The `exit_code` bucket gets its own row (recall, no bar) as context.
4. Also reported, no bars: `missing` recall over expected-`missing` success cases, the verdict mix by bucket, and the code-decided failures (non-zero exit code, Jev not asked) counted apart, because they cost nothing and prove nothing about reading.

Code-level check, run offline before scoring: for every kept case whose log has no exit line and no recognised runner (the native text), `doneRequest` is fed a recorded answer of p = 1.0 and must return `unsure`; any other result is a defect and is reported.

## Data

**Source.** Public GitHub Actions job logs, fetched with the authenticated `gh` CLI (`gh search repos`, `gh run list`, `gh api repos/{o}/{r}/actions/runs/{id}/jobs` and `.../jobs/{id}/logs`). Cached under the scratchpad, never committed. `scripts/real-ci/` fetches, resumes from the cache, and sleeps when the rate limit is low. Logs expire after 90 days, so only runs of the last 80 days before the fetch are used.

**Repositories, deterministic.** Per primary-language bucket (JavaScript, TypeScript, Python, Go, Rust, Java, Ruby, PHP, C#, C++, C, Swift, Kotlin) take `gh search repos --language L --sort stars --archived=false --limit 40` in order; skip forks, repositories without a completed run in the window, and `ripgrep`; accept up to 8 per bucket that yield at least one case. Required: at least 60 distinct repositories in total. The licence (SPDX) of each is recorded.

**Runs and cases.** Per repository, list the last 100 completed runs inside the window; split into failed and succeeded; order each by `sha256(run id)`; inspect runs alternating failed and succeeded, at most 8 runs and 8 jobs per run (ordered by `sha256(job id)`). Cases per repository: at most 5, at most 2 from failed steps. A (workflow, step name) pair gives one case per repository. A top-up pass restricted to failed runs is allowed once if failed-step cases are under 20% of all kept cases. Skipped and cancelled steps and `uses:` steps are excluded; so are `Set up job`, `Post ...` and `Complete job`.

**Step split.** The job log has no step column (`gh run view --job --log` prints `UNKNOWN STEP`). A step starts at a line `##[group]Run <first line of the script>`; the segments, in order, are mapped to the job's steps that are neither skipped nor `Set up job` / `Complete job`. A job whose segment count differs from that step count is dropped and counted.

**Purpose and criterion, by a fixed classifier** over the step name plus the first 600 characters of its script: test (`npm|pnpm|yarn|bun [run] test`, `pytest`, `jest`, `vitest`, `mocha`, `rspec`, `phpunit`, `pest`, `go test`, `cargo test|nextest`, `dotnet test`, `mvn ... test|verify`, `gradle ... test`, `ctest`, `tox`, `nox`, `make test|check`, `bazel test`, `swift test`, `mix test`, `dart test`, `flutter test`, `rake test|spec`, `deno test`, `node --test`, `composer test`, `python -m pytest|unittest`) gives "all tests pass"; lint (`eslint`, `prettier --check`, `stylelint`, `ruff`, `flake8`, `pylint`, `black --check`, `isort --check`, `rubocop`, `golangci-lint`, `go vet`, `cargo clippy`, `cargo fmt --check`, `phpcs`, `phpstan`, `php-cs-fixer`, `ktlint`, `detekt`, `checkstyle`, `spotless`, `shellcheck`, `hadolint`, `yamllint`, `markdownlint`, `biome check|lint|ci`, `clang-tidy`, `cppcheck`, `swiftlint`, `[npm|yarn|pnpm] [run] lint`, `make lint`, `pre-commit`) gives "lint is clean"; build (`[npm|yarn|pnpm|bun] [run] build`, `cargo build|check`, `go build`, `mvn ... package|compile|install`, `gradle ... build|assemble`, `dotnet build|publish`, `make`, `cmake --build`, `msbuild`, `xcodebuild ... build`, `swift build`, `vite build`, `next build`, `webpack`, `docker build`, `python -m build`, `poetry build`, `bazel build`, `ninja`, `zig build`, `sbt compile`) gives "the build succeeds". A step matching more than one class is excluded and counted (multi-purpose); one matching none is not a candidate. Type checkers are not sampled.

**Evidence text.** The step's lines with the transport prefix (timestamp, BOM) removed; `##[group]Run X` becomes `$ X`; the tokens `##[group]`, `##[endgroup]`, `##[command]`, `##[error]`, `##[warning]` and `##[notice]` are removed (a line that is only a group or endgroup marker is dropped); nothing else is changed. A last line `exit code: N` is appended: N is taken from the step's `Process completed with exit code N.` line, or 0 when the step succeeded and has none. This mirrors the documented use of `done` (`{ cmd; echo "exit code: $?"; }`). Then `doneEvidence` (strip ANSI, keep the first 2,000 and last 12,000 characters, as the `done` command does) is applied; characters cut are recorded per case. Redaction runs before anything leaves the machine; a case it stops (a credential-shaped value) is dropped and counted.

**Expected label, fixed in advance.** A step failed if its conclusion is `failure` or its log has a non-zero `Process completed with exit code`: expected `missing` (decided in code by `done`, no request). A step succeeded if its conclusion is `success` and no such marker exists: then expected `met` only if the evidence shows the checks actually ran and each passed, else `missing`, by the labelling convention of the earlier sets: skipped, pending, risky or incomplete tests mean "all tests pass" is not shown; zero tests, "no tests found", or a cache hit or "nothing to do" with no work done mean the criterion is not shown; a warning or notice means "lint is clean" is not shown; a warning does not change "the build succeeds" when no error is printed. A case a labeller calls `ambiguous` is dropped.

**Labelling.** Two separate `claude -p` processes with no repository access and no tools, shown only the criterion, the convention above and the evidence exactly as `done` would pass it on (not the conclusion, not the repository, not the parser facts). Labeller 1 labels every succeeded-step case. Labeller 2, in a separate process, labels a random 30% (those with the lowest `sha256(case id + "label2")`), blind to labeller 1. A case where the two differ, or where either says `ambiguous`, is dropped and listed; raw agreement and Cohen's kappa on the 30% are reported. Cases outside the 30% keep labeller 1's label. Nothing is dropped or relabelled after Jev's answers are seen.

## Scoring

Parser coverage and the code-level check are computed offline first. Then the suite `done-v2-real` (`split: "holdout"`, criterion per case) is recorded once with `eval record` and scored once with `eval score`; the key comes from the keychain and is never printed. Nothing is tuned, no parser is added, no cap or question is changed. If a wrong `met` occurs, the suite's `max_wrong_positive` is set to the observed count (the convention of the earlier sets) and the result is reported as a failure of bar 1.

## What is committed

**Decision on log text.** The question "may the repo commit log excerpts" was put to Jev (`decide`, three options: text only for permissively licensed repositories; no text at all; all text). First ask 0.54 / 0.44 / 0.01 (receipt `rmuqaymlia1f7`), after adding two neutral facts 0.64 / 0.34 / 0.01 (receipt `rmuqayxupkfma`), orders agreeing both times. That is under the 0.90 bar, so the conservative option is taken: **no log text is committed, for any repository, permissive or not.** The repository holds, per case, the repository, run and job identifiers, step number, SHA-256 of the evidence text, label(s), the parsed facts (runner, counts, flags) and the recorded Jev answer. **The suite is therefore not rerunnable through `eval score` from the repository**; the result is rerunnable from the table by `scripts/real-ci/score.mjs`, and the cases can be re-derived by the fetch script only while GitHub still keeps the logs (90 days) and only if the same runs are selected (the selection is deterministic, the run list is not stable over time). This is said in the result.

## Limits, stated now

- Public GitHub Actions only, popular repositories only, workflows with explicit `run:` steps; `uses:` actions that run tests are not sampled; a step classifier of my own picks the sample, so tools that appear in many popular workflows are over-represented.
- The exit line is appended, as the documentation tells users to do; a user who does not append it gets `unparsed` and no `met` for unrecognised tools.
- Labellers are the same model family as the author, two separate processes, no independent human labels; a 30% re-label, not all.
- One Jev model version; recorded answers, not live ones; the sample of one time window.
- Success steps in popular repositories are mostly clean, so expected `missing` among succeeded steps may be rare and the wrong-`met` bound loose; the number is reported, not assumed.
- Redistribution of log text is unresolved, hence no text.
