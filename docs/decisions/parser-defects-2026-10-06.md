# Six parser defects found on 2026-10-06

2026-10-06. A scout pass ran real tools on local synthetic projects (`node --test` on Node 26, `cargo test --no-fail-fast`, `bun test` 1.4.0, Pest, vitest 5.0.3, `tsc`), piped their output through `parseEvidence` and `done` with a simulated `met` answer, and found six ways a failing, cancelled, skipped or partial run could read as clean, or a log could be read as the wrong runner. Each was re-reproduced independently from the saved output before any change. A review of the first fixes then ran more real tools (Pest 5.3 with Collision 8.9, vitest 5.0.3, Node 26.9, bun 1.4.0, tsc 6.0.3, cargo under `set -x`) and reproduced thirteen findings: gaps left in the same six defects, two regressions the first fixes caused, and wording. The rules below are the state after both rounds. None of the output is committed; the tests use invented lines of the same shape ([runners-parser-defects.test.ts](../../test/runners-parser-defects.test.ts)).

These are fixes against rules the repository already documents: the worst case wins in every parser; a cancelled or cut-off run is incomplete; skipped, risky, incomplete and expected-failure tests cap `met` at `unsure` (`done.ts` header); evidence that is not recognised can never be `met`. The rules are fitted to the reproductions. This is not a measurement and says nothing about recall on logs not seen.

## The defects and the rules

1. **`node:test` cancelled, failing list, todo, expected failure.** `ℹ cancelled 1` was ignored, so a timed-out test in a run whose summary said `fail 0` read as a clean pass; the names under `✖ failing tests:` were never counted (the flag that skipped them never reset, so a later run's `✖` lines were skipped too); `ℹ todo 1` was not a skip, and the skip markers did not strip the `ℹ` prefix; a test marked `expectFailure` (Node 26 prints `✔ name (Xms) # EXPECTED FAILURE`, TAP `ok 2 - name # EXPECTED FAILURE`, and counts it under `pass`) read as a plain pass. Rule: cancelled N above 0 adds N failures and marks the run `incomplete` (the documented cap for a cancelled run); every `✖` name in the failing list counts, with or without a `(Xms)` duration, and the list ends at the next unindented line that is not blank, `test at`, `✖` or `⚠`; a failing list with no entry at all (a cut-off log) still counts one failure; a `⚠` entry in the list is a failing todo test, which node counts under `todo`, not `fail`, so it is not a failure, and neither is a TAP `not ok N - name # TODO` or `# SKIP`; `todo` adds to `skipped`; a passing line with `# EXPECTED FAILURE` adds to `expected_failures` and is a skip marker; `skipTokens` strips a leading `ℹ` like `#`. A hook failure that cancels two subtests counts 3 (the suite and both subtests) where node prints `fail 0`, `cancelled 2`: worst case, kept.
2. **`cargo test --no-fail-fast`.** The closing `error: N targets failed:` was not a failure marker, so a tail that cut off the failing target's `test result: FAILED` read as all passed. Rule: that line, anchored at the start, is at least N failures. With no exit line the failure reaches Jev as `failed: 1` and Jev decides; with `exit code: 0` it is a conflict (`unsure`).
3. **Exit lines.** The exit-line pattern matched inside source frames (`8 |   test("exits with exit code 0 on --help"` in a bun failure, which gave `exit_code: 0` on a failing run), test and suite titles (a passing `✔ returns exit code 2 ...`, a node `▶ exit code 2 handling` suite header or a TAP `# Subtest: exit code 2 handling` gave a false `missing`) and assertion messages (bun prints a thrown `expected exit code 0, got 2` as `error: expected exit code 0, got 2`, which gave `exit_code: 0` on a failing run), and read `exit code 0xC0000005` as 0. Rule ([exit-code-only-met.md](exit-code-only-met.md) and [exit-code-only-lint-wide.md](exit-code-only-lint-wide.md) are unchanged), one function in `util.ts`:
   - a match never counts when the line starts with a source-frame gutter (optional `>`, a line number, `|`), with a passing, skipped or title marker (`✔ ✓ √ ○ ↓ ﹣ ▶`, `(pass)`, `(skip)`, `(todo)`, `ok N`, `# Subtest:`), when the phrase sits inside an open quote (an odd number of `"`, `'` or backticks before it, apostrophes inside words ignored, so `'/nix/store/x.drv' failed with exit code 1` and `didn't exit successfully` still count), when the words before it end in `expected`, `expect`, `should`, `want` or `assert...`, or when the line goes on with `, got`, `received`, `actual`, `want` or `expected` (optionally after `but`);
   - a line that starts with a failure marker (`✖ × ✗ ✕ ✘ ● ⚠`, `(fail)`, `not ok N`) keeps a non-zero code: it comes from a failed run, so `✖ Command failed with exit code 1` is still `missing`. Only a 0 on such a line is dropped, since there it can only be a failing test's title;
   - `exit_lines` (sent to Jev) is still the matched text up to the number, so the request of every case without these shapes is unchanged.

   The function serves `parseEvidence` and the build parsers' exit codes (`exitCodes`, read by the `nix build` parser). The `cargo build` check for output after `Finished` keeps its own looser match from before: the first round routed it through the shared rule, which dropped a traced `+ echo 'exit code: 0'` (`set -x` under bash or zsh) or a prompt's `✔ exit code: 0` and capped a clean build as incomplete. That check only needs to know a line is an exit or echo line, not its value. The `nix build` parser reads its exit codes through the shared rule and marks a run without errors and without an exit code incomplete; a nix log whose only exit line the rule drops was not reproduced. **Deviation from the brief:** the brief said to reject a number followed by hex; a hex code is instead read as its value (`0xC0000005` is 3221225477, non-zero, so `missing` without asking Jev). Rejecting it lost the only non-zero exit signal of a crashed cargo test binary and left it to Jev; reading it can only turn a case towards `missing`. No eval case has a hex exit code.
4. **Pest.** Pest's `Tests:    1 risky, 1 incomplete, 1 passed (1 assertions)` is read by the `jest` parser, which dropped `risky` and `incomplete`; `Tests:    2 risky (0 assertions)` was not read at all and fell back to `exit code: 0`; Collision pluralises todo (`Tests:    2 todos, 1 passed`), which neither the parser nor the skip markers read. Rule: `risky`, `incomplete` and `todo`/`todos` count as skipped (as the PHPUnit parser already does), and any of them is enough for a `Tests:` line to be a summary. The runner keeps the `jest` label: labelling lines with `(N assertions)` as `pest` would change the facts of the recorded hold-out case `h6-f-07` and make its answer stale, and a label only for risky lines would be a rule nobody could predict.
5. **vitest expected fail.** `Tests  1 passed | 1 expected fail (2)` was read as 1 passed. Rule: `N expected fail` is `expected_failures`, the fact that already caps `met` for pytest xfail and unittest expected failures.

   For 4 and 5, the parsers keep their counts from the last summary of a log, as they already did for `skipped` ([skip-markers.test.ts](../../test/skip-markers.test.ts) encodes this for a vitest workspace). In a log with two runs (`pest t5 && pest t4`, `vitest run unit && vitest run int`) an earlier run's risky, incomplete or expected-fail count was therefore lost. Rule: `risky`, `incomplete`, `todos` and the two-word `expected fail` are skip-marker words, so such a count anywhere in the log caps `met` through the skip markers, the same path an earlier `skipped` count already takes. The markers are not part of the facts sent to Jev, so no request changes.
6. **dotnet claimed tsc.** The unanchored `error [A-Z]{2,4}\d{3,5}:` read `file(1,7): error TS2322:` as a dotnet build error, so every tsc log carried a second, `dotnet test`, runner. Rule: a dotnet build error needs the MSBuild shape `origin: error CODE:` (`file(1,2): error CS1002:`, `CSC : error CS5001:`, `App.csproj : error NU1101:`) and a code other than `TS`. tsc uses the same canonical shape, so the `TS` prefix is the only thing that tells them apart. `Build FAILED.` still makes a failing dotnet run. The first round left tsc error lines behind a prefix with no parser at all, because the tsc patterns are anchored at the start of the line and the loose dotnet pattern had been their only reader: a prefixed error next to a passing vitest or node:test run with `exit code: 0` went from a conflict to `met`, and Angular's `Error: src/x.ts:5:3 - error TS2322:` or `- error NG8001:` with `exit code: 0` went from `unsure` to `met`. Rule: the tsc patterns accept one known prefix before the anchored shape (a monorepo task prefix such as turbo `web:typecheck: `, lerna `@acme/web: ` or pnpm `packages/web typecheck: `, a bracketed `[web] `, a compose `web-1  | `, an ISO CI timestamp, BuildKit `#12 4.123 `, Angular `Error: ` or webpack `ERROR in `), and read `NG` codes as well as `TS` codes. Such a line is a tsc error, so with `exit code: 0` it is a conflict (`unsure`), with a non-zero code `missing`, and with no exit line the error count reaches Jev. Free text is still not read: a TS error inside a `NOTE ...:` line does not count (runners-js.test.ts).

## Checks

- First round: 14 tests, all failing on `HEAD` (a snapshot copy) and passing after. Review round: 10 more, all failing on the first-round tree (a snapshot copy) and passing after; of the 24, 22 fail on `HEAD`, and the two that pass there guard the first round's regressions (cargo trace lines, prefixed tsc and NG errors). Each defect has an end-to-end `done` check with a simulated `met` answer that gives `unsure` or `missing`, and a clean run of the same runner that stays `met` (for 6: a clean `dotnet test` summary and `npx tsc --noEmit` with `exit code: 0`).
- Facts, recomputed for all 357 eval cases with evidence: against `HEAD`, the request sent to Jev and the simulated verdict are unchanged for all 357, and the skip markers too; `parseEvidence` differs only for `done-v2/d-tsc-errors` and `done-v2/h-tsc-nonzero`, which lose the spurious `dotnet test` runner and stop at their non-zero exit code before any request. Against the first-round tree, nothing changed. `eval score --suite all --fail-on violated` gives the same output before and after the review round (the stop suites included), so no recorded answer went stale.
- The review's own reproductions (real Pest, vitest, node, bun, tsc and cargo output) and about 12,700 texts from the eval files, docs, tests and scout logs were compared between the first-round tree and the result. Every change is one of the rules above; none goes from `failed` to `passed` in the stop gate except title lines no longer read as non-zero exit codes and failing todo tests no longer read as failures.

## Limits

Fitted to the reproductions, by the same model family that found them; the fixtures are invented. The tsc prefix list is an allowlist: an error line behind a prefix not on it is still read by no parser, and with `exit code: 0` and no other runner can reach `met` for a build criterion (as any unrecognised output with an exit code can, per exit-code-only-met.md). The assertion-message rule knows a few English phrasings; `should exit with exit code 0` or a message in another language is still read as an exit code. It also drops a real exit report that goes on in assertion words (`Process exited with exit code 1, expected 0`), non-zero code included; no log seen has that shape. A failure-marker line with a 0 is dropped even if some tool prints a real exit line that way. `⚠` counts as a failure marker; in node's spec reporter it only leads a failing todo test, so such a title with a non-zero code gives `missing` where the todo cap would give `unsure`. Out of scope and unchanged: a parsed runner hiding a failing unrecognised one (`node --test && bun test`), a `bun test` parser, and the copy of the old exit pattern in `scripts/done-bar/lib.mjs` (analysis scripts, not the shipped parser).
