# Six parser defects found on 2026-10-06

2026-10-06. A scout pass ran real tools on local synthetic projects (`node --test` on Node 26, `cargo test --no-fail-fast`, `bun test` 1.4.0, Pest, vitest 5.0.3, `tsc`), piped their output through `parseEvidence` and `done` with a simulated `met` answer, and found six ways a failing, cancelled, skipped or partial run could read as clean, or a log could be read as the wrong runner. Each was re-reproduced independently from the saved output before any change. A review of the first fixes then ran more real tools (Pest 5.3 with Collision 8.9, vitest 5.0.3, Node 26.9, bun 1.4.0, tsc 6.0.3, cargo under `set -x`) and reproduced thirteen findings: gaps left in the same six defects, two regressions the first fixes caused, and wording. The rules below are the state after both rounds. None of the output is committed; the tests use invented lines of the same shape ([runners-parser-defects.test.ts](../../test/runners-parser-defects.test.ts)).

These are fixes against rules the repository already documents: the worst case wins in every parser; a cancelled or cut-off run is incomplete; skipped, risky, incomplete and expected-failure tests cap `met` at `unsure` (`done.ts` header); evidence that is not recognised can never be `met`. The rules are fitted to the reproductions. This is not a measurement and says nothing about recall on logs not seen.

## The defects and the rules

1. **`node:test` cancelled, failing list, todo, expected failure.** `ℹ cancelled 1` was ignored, so a timed-out test in a run whose summary said `fail 0` read as a clean pass; the names under `✖ failing tests:` were never counted (the flag that skipped them never reset, so a later run's `✖` lines were skipped too); `ℹ todo 1` was not a skip, and the skip markers did not strip the `ℹ` prefix; a test marked `expectFailure` (Node 26 prints `✔ name (Xms) # EXPECTED FAILURE`, TAP `ok 2 - name # EXPECTED FAILURE`, and counts it under `pass`) read as a plain pass. Rule: cancelled N above 0 adds N failures and marks the run `incomplete` (the documented cap for a cancelled run); every `✖` name in the failing list counts, with or without a `(Xms)` duration, and the list ends at the next unindented line that is not blank, `test at`, `✖` or `⚠`; a failing list with no entry at all (a cut-off log) still counts one failure; a `⚠` entry in the list is a failing todo test, which node counts under `todo`, not `fail`, so it is not a failure, and neither is a TAP `not ok N - name # TODO` or `# SKIP`; `todo` adds to `skipped`; a passing line with `# EXPECTED FAILURE` adds to `expected_failures` and is a skip marker; `skipTokens` strips a leading `ℹ` like `#`. A hook failure that cancels two subtests counts 3 (the suite and both subtests) where node prints `fail 0`, `cancelled 2`: worst case, kept.
2. **`cargo test --no-fail-fast`.** The closing `error: N targets failed:` was not a failure marker, so a tail that cut off the failing target's `test result: FAILED` read as all passed. Rule: that line, anchored at the start, is at least N failures. With no exit line the failure reaches Jev as `failed: 1` and Jev decides; with `exit code: 0` it is a conflict (`unsure`).
3. **Exit lines.** The exit-line pattern matched inside source frames (`8 |   test("exits with exit code 0 on --help"` in a bun failure, which gave `exit_code: 0` on a failing run), test and suite titles (a passing `✔ returns exit code 2 ...`, a node `▶ exit code 2 handling` suite header or a TAP `# Subtest: exit code 2 handling` gave a false `missing`) and assertion messages (bun prints a thrown `expected exit code 0, got 2` as `error: expected exit code 0, got 2`, which gave `exit_code: 0` on a failing run), and read `exit code 0xC0000005` as 0. Rule ([exit-code-only-met.md](exit-code-only-met.md) and [exit-code-only-lint-wide.md](exit-code-only-lint-wide.md) are unchanged), one function in `util.ts`:
   - a match never counts when the line starts with a source-frame gutter (optional `>`, a line number, `|`), with a passing, skipped or title marker (`✔ ✓ √ ○ ↓ ﹣ ▶`, `(pass)`, `(skip)`, `(todo)`, `ok N`, `# Subtest:`), when the phrase sits inside an open quote (an odd number of `"`, `'` or backticks before it, apostrophes inside words ignored, so `'/nix/store/x.drv' failed with exit code 1` and `didn't exit successfully` still count), when the words before it end in `expected`, `expect`, `should`, `want` or `assert...`, or when the line goes on with `, got`, `received`, `actual`, `want` or `expected` (optionally after `but`);
   - a line that starts with a failure marker (`✖ × ✗ ✕ ✘ ● ⚠`, `(fail)`, `not ok N`) keeps a non-zero code: it comes from a failed run, so `✖ Command failed with exit code 1` is still `missing`. Only a 0 on such a line is dropped, since there it can only be a failing test's title;
   - `exit_lines` (sent to Jev) is still the matched text up to the number, so the request of every case without these shapes is unchanged.

   The function serves `parseEvidence` and the build parsers' exit codes (`exitCodes`, read by the `nix build` parser). The `cargo build` check for output after `Finished` keeps its own looser match from before: the first round routed it through the shared rule, which dropped a traced `+ echo 'exit code: 0'` (`set -x` under bash or zsh) or a prompt's `✔ exit code: 0` and capped a clean build as incomplete. That check only needs to know a line is an exit or echo line, not its value. The `nix build` parser reads its exit codes through the shared rule and marks a run without errors and without an exit code incomplete; a nix log whose only exit line the rule drops was not reproduced. **Deviation from the brief:** the brief said to reject a number followed by hex; a hex code is instead read as its value (`0xC0000005` is 3221225477, non-zero, so `missing` without asking Jev). Rejecting it lost the only non-zero exit signal of a crashed cargo test binary and left it to Jev; reading it can only turn a case towards `missing`. No eval case has a hex exit code.
4. **Pest.** Pest's `Tests:    1 risky, 1 incomplete, 1 passed (1 assertions)` is read by the `jest` parser, which dropped `risky` and `incomplete`; `Tests:    2 risky (0 assertions)` was not read at all and fell back to `exit code: 0`; Collision pluralises todo (`Tests:    2 todos, 1 passed`), which neither the parser nor the skip markers read. Rule: `risky`, `incomplete` and `todo`/`todos` count as skipped (as the PHPUnit parser already does), and any of them is enough for a `Tests:` line to be a summary. The runner keeps the `jest` label: labelling lines with `(N assertions)` as `pest` would change the facts of the recorded hold-out case `h6-f-07` and make its answer stale, and a label only for risky lines would be a rule nobody could predict.
5. **vitest expected fail.** `Tests  1 passed | 1 expected fail (2)` was read as 1 passed. Rule: `N expected fail` is `expected_failures`, the fact that already caps `met` for pytest xfail and unittest expected failures.

   For 4 and 5, the parsers keep their counts from the last summary of a log, as they already did for `skipped` ([skip-markers.test.ts](../../test/skip-markers.test.ts) encodes this for a vitest workspace). In a log with two runs (`pest t5 && pest t4`, `vitest run unit && vitest run int`) an earlier run's risky, incomplete or expected-fail count was therefore lost. Rule: `risky`, `incomplete`, `todos` and the two-word `expected fail` are skip-marker words, so such a count anywhere in the log caps `met` through the skip markers, the same path an earlier `skipped` count already takes. The markers are not part of the facts sent to Jev, so no request changes.
6. **dotnet claimed tsc.** The unanchored `error [A-Z]{2,4}\d{3,5}:` read `file(1,7): error TS2322:` as a dotnet build error, so every tsc log carried a second, `dotnet test`, runner. Rule: a dotnet build error needs the MSBuild shape `origin: error CODE:` (`file(1,2): error CS1002:`, `CSC : error CS5001:`, `App.csproj : error NU1101:`) and a code other than `TS`. tsc uses the same canonical shape, so the `TS` prefix is the only thing that tells them apart. `Build FAILED.` still makes a failing dotnet run. The first round left tsc error lines behind a prefix with no parser at all, because the tsc patterns are anchored at the start of the line and the loose dotnet pattern had been their only reader: a prefixed error next to a passing vitest or node:test run with `exit code: 0` went from a conflict to `met`, and Angular's `Error: src/x.ts:5:3 - error TS2322:` or `- error NG8001:` with `exit code: 0` went from `unsure` to `met`. Rule: the tsc patterns accept one known prefix before the anchored shape (a monorepo task prefix such as turbo `web:typecheck: `, lerna `@acme/web: ` or pnpm `packages/web typecheck: `, a bracketed `[web] `, a compose `web-1  | `, an ISO CI timestamp, BuildKit `#12 4.123 `, Angular `Error: ` or webpack `ERROR in `), and read `NG` codes as well as `TS` codes. Such a line is a tsc error, so with `exit code: 0` it is a conflict (`unsure`), with a non-zero code `missing`, and with no exit line the error count reaches Jev. Free text is still not read: a TS error inside a `NOTE ...:` line does not count (runners-js.test.ts).

## Limits

Fitted to the reproductions, by the same model family that found them; the fixtures are invented. The tsc prefix list is an allowlist: an error line behind a prefix not on it is read by no parser (before the first round the loose dotnet pattern read it, as a `dotnet test` error, which gave a conflict), and with `exit code: 0` and no other runner can reach `met` for a build criterion (as any unrecognised output with an exit code can, per exit-code-only-met.md). The follow-up below found the realistic case of that change (`gh run view --log`) and strips GitHub's prefixes before parsing. The assertion-message rule knows a few English phrasings; `should exit with exit code 0` or a message in another language is still read as an exit code. It also drops a real exit report that goes on in assertion words (`Process exited with exit code 1, expected 0`), non-zero code included; no log seen has that shape. A failure-marker line with a 0 is dropped even if some tool prints a real exit line that way. `⚠` counts as a failure marker; in node's spec reporter it only leads a failing todo test, so such a title with a non-zero code gives `missing` where the todo cap would give `unsure`. Out of scope and unchanged: a parsed runner hiding a failing unrecognised one (`node --test && bun test`), a `bun test` parser (added in the follow-up below), and the copy of the old exit pattern in `scripts/done-bar/lib.mjs` (analysis scripts, not the shipped parser).

A second review ran the fixed tree (`ba2231d`) against real tools again (Node 26.9 spec, TAP and dot reporters, bun 1.4.0, vitest 5.0.3, jest 30, Pest 5.3, tsc 7.0.2, a real `gh run view --log-failed`), as full logs and through `| tail -n 5/10/20/40` with `; echo "exit code: $?"`, with done's clip applied. It found:

| | Finding | Kind |
|---|---|---|
| P1 | A tsc error in `gh run view --log` output (`job<TAB>step<TAB>ISO-timestamp line`) with gh's `exit code: 0` gave `met` | Regression from rule 6: the loose dotnet pattern had been its only reader (a conflict) |
| P2 | `##[error]Process completed with exit code N.` behind a timestamp was never read (the phrase sat past the 60-character window), so a failed CI log with `exit code: 0` gave `met` | Pre-existing |
| P3 | `node --test \| tail -n 20`: Node 26 prints the summary before the failing list, so the window holds only the last failure's details and tail's exit code 0 gave `met` | Pre-existing |
| P4 | A todo with a reason prints `⚠ name (Xms) # reason`, not `# TODO`; with `ℹ todo N` above a tail or in the clip's omitted middle, the run gave `met` | Pre-existing; rule 1 did not cover the reason form |
| P5 | `bun test \| tail`: no bun parser, so `exit code: 0` gave `met` | Pre-existing (out of scope in the first round) |
| P6 | The new skip words cap a true pass at `unsure` when a test's own stdout prints `Completed: 1, Incomplete: 2` | Regression (low): a false cap, never `met` |

Rules (fitted fixes, not a measurement):

1. **P1, P2.** `parseEvidence` and the skip markers strip one GitHub prefix per line first: gh's `job<TAB>step<TAB>2026-10-07T00:26:55.4401234Z ` and the raw log's `2026-10-07T00:26:55.4401234Z `, with an optional byte order mark, the shapes `scripts/real-ci/lib.mjs` strips. The tsc patterns then read the error, and `##[error]Process completed with exit code 2.` is an exit line with no new lead (32 characters before the phrase). A failed CI log is `missing`; a tsc error with only gh's `exit code: 0` is a conflict. A timestamp inside a line stays; `exit_lines` holds the stripped text.
2. **P3.** With no node:test summary and no other failure count (`✖ name`, TAP `not ok`, `fail N`, `cancelled N`, an empty failing list), one of these whole-line shapes is one failure and marks the run incomplete: `test at file:line:col` not followed by a `⚠` entry, `code: 'ERR_ASSERTION',` or `'ERR_TEST_FAILURE',`, `failureType: '...',`, `diff: 'simple'`, a `TestContext.<anonymous>` or `node:internal/test_runner/` stack frame, `'test failed'`, `'test timed out after Nms'`, `'test did not finish before its parent and was cancelled'`. The internal-frame and `diff` shapes go beyond the brief: a failing hook's `tail -n 5` holds only internal frames, the shortest assertion windows only `operator` and `diff`. Details after a `⚠` entry are a failing todo's. With a summary, the summary decides.
3. **P4.** `⚠ name (Xms) # reason`, `﹣ name (Xms) # reason` and `✔ name (Xms) # reason` (a passing todo; `# EXPECTED FAILURE` excluded) count as skipped, by distinct name, with or without a summary. Node adds ` # ...` after the duration only for skip, todo and expected failure. With a summary, `skipped` is the larger of the summary's count and the distinct names, never their sum.
4. **P5.** A `bun test` parser reads ` N pass/fail/skip/todo/error` next to `Ran N tests across N files.`, and `(fail)`, `(skip)`, `(todo)` lines. It claims a log only when it shows a failure (` N fail` or ` N error` above 0, or a `(fail)` line; `(fail)` with no summary is incomplete). **Deviation from the brief:** clean bun logs are left to their exit code, because parsing them changes the facts of the recorded case `done-v2-h4/h4-c-02`, and `eval score` refuses a stale recording (the reason rule 4 kept Pest's `jest` label). A failing bun log with no exit line now reaches Jev as facts (`failed: N`) like every parsed runner, instead of being unparsed; the two first-round bun fixtures were rewritten to assert that.
5. **P6.** Checked, not changed: a zero count is never a skip marker (`Incomplete: 0`, `Todos: 0`, `0 risky`, `0 expected fail` give none on both trees). A non-zero count in a passing test's stdout caps at `unsure`, as `Pending: 2` already did. The lens's fix (count the new words only on labelled summary lines) is left as a limit.

Checks: `test/runners-followup.test.ts` has 13 tests; 9 fail on `e1174dc` (a snapshot copy) and pass after, 4 are clean-pass guards that pass on both. Facts recomputed on `e1174dc` and after for all 357 done eval cases (parse, skip markers, request, simulated verdicts) and 48 stop cases (transcript facts and state): identical; `eval score --suite all` output is byte-identical. Of the review's 181 real logs, 34 change, all away from `met` (25 `met` become `missing` or `unsure`); of its 496 prefixed variants only the 120 gh ones change, gh `met` going from 108 to 4 (node expected failures under a tail, where nothing is left to parse). Of the regression lens's 5,727 texts, 7 change, each by one of the rules.

Limits: only GitHub's two prefixes are stripped (not Jenkins' `00:26:55  ` or others). A window too short for any shape, a head-cut log, or a two-run tail whose clean summary follows the other run's error block reads as before. A clipped todo run whose tail starts inside a todo's error block gives a conflict rather than the skip reason (both `unsure`). As first written, rule 2 also read a passing run's logged `AssertionError` as a node:test failure, not only in a summary-less window: full jest, vitest and bun logs with their own clean summary lost `met`, and the Stop gate marked such a check failed. The re-review below found it (F7) and narrowed the rule. The TTY form `✗ name [Xms]` is not read as a bun failing name; the counts are.

## Re-review of the follow-up (2026-10-07)

A re-review ran the follow-up tree against real tools again (Node 26.9 spec, dot and TAP reporters, jest 30.5, vitest 5.0.3, bun 1.4.0, turbo, nx 23.2, npm 11.19, esbuild, a real nodejs/undici job log from `gh run view --log`), as full logs and as `| tail -n N` windows with `; echo "exit code: $?"`, and reproduced seven findings:

| | Finding | Kind | Outcome |
|---|---|---|---|
| F1 | A `⚠` line inside a thrown message (`Error: lint reported warnings:` then `⚠ no-unused-vars: ...`) made a todo the owner of the details, so the `TestContext` frames after it were ignored and `tail -n 8..22` gave `met` | Regression from rule 2 above | Fixed |
| F2 | A timed-out or cancelled job's gh log with no exit line: stripping the prefixes made earlier steps' pass summaries readable, so `unsure` became `met` | Regression from rule 1 above | Fixed for parsed runners; limit with no runner |
| F3 | Error blocks with only library, async or props lines (esbuild, `ENOENT`, `execFileSync`, deep recursion, a throw in a timer) carry none of rule 2's shapes; `tail -n 1..15` gives `met` | Pre-existing, narrowed by rule 2 | Limit (done level) |
| F4 | turbo, nx, `bun --filter`, `bun run` and `npm test -ws` under a tail gave `met` | Pre-existing | Fixed where the window holds the wrapper's report |
| F5 | TAP: a describe-level `after()` hook failure prints `# fail 0`; `tail -n 5..28` gave a parsed `met` | Pre-existing | Fixed for `tail -n 15..28` |
| F6 | bun: `snapshots: 1 failed` was not read, and `bun test -t x` matching no test (exit 1) gave `met` | Pre-existing | Fixed; `tail -n 1..2` a limit |
| F7 | Rule 2's `code: 'ERR_ASSERTION',` and `diff: 'simple'` are props of every `AssertionError`: a passing jest, vitest or bun run that logs one lost `met`, and the Stop gate marked the check failed | Regression from rule 2 above (a false cap, never `met`) | Fixed |

Rules (fitted fixes, not a measurement):

1. **F1.** Only a node entry line, `✖ name (Xms)` or `⚠ name (Xms)` with an optional ` # reason`, owns the details after it. A `⚠` or `✖` line inside an error message does not.
2. **F7.** `code: 'ERR_ASSERTION',` and `diff: 'simple'` or `'full'` count only when the log holds no other runner's summary (jest `Tests:`, vitest `Tests  N passed|failed`, bun `Ran N tests across N files.`, mocha `N passing`). The node:test-only shapes (`ERR_TEST_FAILURE`, `failureType`, `TestContext.<anonymous>` and `node:internal/test_runner/` frames, the `'test ...'` messages, `test at file:line:col`) count as before, so the shortest node windows (`operator`, `diff`, `}`) are still one failure.
3. **F2.** After the prefixes are stripped, `##[error]The operation was canceled.`, `##[error]The job ... has exceeded the maximum execution time` or `##[error]The runner has received a shutdown signal` at the start of a line marks every parsed runner incomplete, so `met` is capped (`incomplete_run`). The annotation is not read as an exit code or a runner: five eval cases hold one, four with no parsed runner (`done-v2-h2/h2-b-03`, `done-v2-h3/h3-a-04`, `h3-d-08`, `done-v2-h4/h4-c-07`) and one whose `next build` runner is already incomplete with exit 143 (`h4-f-07`), and reading it would change their facts.
4. **F4.** A wrapper's own exit report is read for a non-zero code only, and only when the log's exit lines show no non-zero code; it then comes first in `exit_lines`. Shapes, each seen in real output: turbo `ERROR  run failed: command  exited (N)` and a task's `pkg#task:  ERROR  command (...) ... exited (N)`; nx ` NX   Running target(s) ... failed` (nx's title prints no code; read as 1, the code nx exits with); `bun run`'s `error: script "x" exited with code N`; `bun --filter`'s `pkg script: Exited with code N`; concurrently's `[name] cmd exited with code N`; npm 10+ `npm error code N`, bare or behind one `task: ` prefix. A zero code adds nothing, so a wrapper report can never lead to `met`. Reading only as a fallback keeps the facts of `done-v2-h5/h5-e-05` (compose `tests-1 exited with code 1` next to `compose exit code: 1`), whose `exit_lines` would gain the wrapper line otherwise. The bun parser also reads a line behind one `pkg script: ` prefix (`bun --filter`, `pnpm -r`) when the bare line is not a bun shape, so `(fail) parser: handles x` keeps its name.
5. **F5.** A TAP YAML line `failureType: 'hookFailed'` (no trailing comma) or a YAML frame `TestHook.run`, `Suite.runHook` or `Test.runHook (node:internal/test_runner/...)` is one failure when the summary counts `fail 0` and `cancelled 0` and the nearest TAP entry above it is not `not ok ... # TODO` or `# SKIP`. Wider shapes (any `failureType`, `code: 'ERR_TEST_FAILURE'`, any internal frame) were tried: in 154 todo-TAP windows whose `not ok ... # TODO` line was cut they read the todo's YAML as a failure, turning the `skipped_tests` cap into a conflict and the Stop gate's `passed` into `failed`. The hook shapes do not occur in a todo's YAML.
6. **F6.** `snapshots: ... N failed` with N above 0 is a failure (incomplete without the `Ran` line); `snapshots: +3 added`, `2 passed, 1 added` and ` 5 snapshots, 5 expect() calls` are not. `error: regex "x" matched 0 tests` with no summary and no `(fail)` line is a bun runner with one error, marked incomplete: bun exits 1 there, so `exit code: 0` is a conflict and the Stop gate reads the check as failed. A runner with all counts at zero would have read as a clean parsed run in the Stop gate (`passed`).

Checks: `test/runners-followup-2.test.ts` has 7 tests; 6 fail on the follow-up tree and on `e1174dc` (snapshot copies) and pass after, and the guard (zero codes, unchanged exit lines, prose) passes on all three. Facts recomputed for all 357 done and 48 stop eval cases (parse, skip markers, request, simulated verdicts, stop facts and state): identical to `e1174dc`; `eval score --suite all` output is byte-identical. Against the follow-up tree, over the review texts (1,037 real logs, 1,568 prefixed variants, 5,657 tail windows and gh logs, 75 regression logs), 438 texts change (copies of the same log in the real and regression sets merged; the after-hook windows sit in two sweep directories and count twice): 269 leave `met`, all failing runs, and 8 return to `met`, the F7 passes (bun, jest and verbose vitest logs with a logged assertion, full and `tail -n 10/20/40`). Every other change is a failing run going from `unsure` to `missing`. In the Stop gate only those 8 go from failed to passed, and only failing runs from passed to failed. Nothing changes in the 676 gh run logs (raw and stripped), 889 eval texts, 4,857 doc blocks and 2,180 test strings.

Limits:

- F2: a cancelled job with no parsed runner and `exit code: 0` (a real undici job cancelled in its first test step, through `gh run view --log` with the echo) is still `met` from the exit code alone, as on `e1174dc`. Reading the annotation as a failure would change the facts of the eval cases above; it needs a cap in `done`.
- F3: unchanged. Library and async frames and an error's own props are not node:test-specific: jest, vitest and bun print the same blocks for logged errors (F7), so a runner cannot claim them, and the reviewer's six-space frame shape also claimed a mocha log's frames, adding a failed, incomplete `node:test` runner to the facts of `done-v2-h3/h3-d-04`. The fitting fix is a cap in `done` on exit-code-only evidence that ends in a stack frame or a props block; `done.ts` was out of scope.
- F4: a tail that holds only the last, passing workspace of `npm test -ws` (npm goes on after a failing one: `tail -n 1..30` in the reproduction) or only nx's footer below its title (`tail -n 1..11`) still gives `met`. `npm ERR! code N` (npm 9 and older) is not read; no real log with it was seen. A log that prints a wrapper report itself and still passes (a test's own `[worker] ... exited with code 1`, a recovered `npm error code 1` before a retry) is now `missing`.
- F5: `tail -n 1..14` of the reproduction stays `met`: those windows hold only summary lines (the shortest not even a full summary, so the exit code decides) and frames that passing suites also print.
- F6: a bun window of ` N expect() calls` and `Ran N tests` alone (`tail -n 1..2`) holds no failure count and stays `met`; so does a todo or skip count cut off by a tail.
- Seen in passing, not from this review: a whole-run `gh run view --log` whose last 12,000 characters (done's clip) are another job's cleanup reads as that job (a head cut, out of scope); and the Stop gate parses raw tool output, where a coloured passing title (`ESC[32m✔ exit code 2`) is read as exit code 2 because ANSI is not stripped before the exit rule (a false `failed`, never `met`; the same on `e1174dc`).
