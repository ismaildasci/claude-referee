# Result: the lint warning cap for criteria that name the linter, and an oxlint parser

Result of [lint-cap-tool-names.md](lint-cap-tool-names.md), 2026-10-07. The three rules were built as registered; the numbers below are replays of recorded answers, with no new Jev request. This is a fix toward the documented rule, fitted to cases seen in real use, not a clean test.

## What was built

1. `CLEAN_CRITERION` in `src/cli/commands/done.ts` also matches the linter names `oxlint`, `eslint`, `biome`, `ruff`, `phpstan`, `pint`, `stylelint`, `golangci-lint`, `clippy`, `rubocop`, `phpcs`, `flake8`, `pylint`, `shellcheck` and `markdownlint` as whole words (the list lives in `src/engine/runners/kinds.ts`). Nothing else in the cap changed.
2. `src/engine/runners/oxlint.ts`, written from real oxlint 1.87.0 output captured on a scratch project (files with warnings, with errors, with a parse error, and clean; `--format` default, github, agent, unix and stylish; piped and on a terminal; `--quiet`, `--silent`, `--max-warnings=0`, `--deny-warnings`, a path with no files, and `| tail -n 1`, `2`, `3`). It reads `Found N warning(s) and M error(s).` and `Finished in Xms on N file(s) with R rules using T threads.` at the start of a line, or after npm's spinner frames (`⠋⠙⠹…` or `-\|/`, as in npm 11's `lib/utils/display.js`) and `script`'s `^D` echo, which a terminal capture of `npx oxlint` leaves in front of the line once the colour codes are stripped (only `\` and Braille frames were seen; all four ASCII frames are accepted, so a diff's removed line `-Found 2 warnings and 0 errors.` is read as oxlint's too). Warnings and errors come from the `Found` lines (summed over runs), with the diagnostic heads as a floor (`  !` and `  ⚠` warnings, `  x` and `  ×` errors, a rule id or a `,-[` / `╭─[` location line after them); errors list `file:line:col rule`. No `Found` line (a `| tail -n 1` window) or 0 files is incomplete. The facts carry the code-only `build_only` mark (no test results, never sent to Jev), so a test criterion backed only by a build and oxlint is still capped as no tests run; that cap's next step now says "only a build or a lint run".
   - It claims a log only when it shows a warning or an error, or is incomplete. A clean log (every `Found` line 0 and 0, no diagnostic head, files linted) is not claimed and keeps its exit-code reading, as a clean `bun test` log does. The first build claimed it, and a clean oxlint summary next to another tool's warnings then gave `met`: parsed trust skips the warning and problem wording check, and the facts held only oxlint's zeros, so neither the cap nor Jev saw the other tool. With stylelint's `⚠ 1 problem (0 errors, 1 warning)` or markdownlint's `error MD022` lines before or after a clean oxlint run and `exit code: 0`, "lint is clean", "all lint checks pass" and "stylelint and oxlint pass" are `unsure` (`warning_in_log`) again, as on base for the first two.
   - The agent, unix and stylish formats print neither line and are not claimed; stylish's `✖ N problems (E errors, W warnings)` stays eslint's. Inside a Claude Code session oxlint 1.87 prints its agent format without being asked (`CLAUDECODE=1` alone is enough), one `file:line:col: warning rule: message` line per diagnostic and nothing for a clean run, so those logs keep the exit-code reading and are covered by rule 1.
3. `src/engine/runners/kinds.ts` maps every runner name a parser emits to the kinds it covers (test, lint, build, typecheck), `flutter test` (emitted by the dart parser) included; a test fails when a parser name or an emitted name has no entry. A runner covers typecheck when its output reports the compiler's type errors (`tsc`, `next build`, `cargo build`/`check`, `clippy`, `golangci-lint`, `msbuild`, `swift build`, `maven`); `tsc` also covers build, `maven` build and test. When trust is `parsed` and a criterion that is not `met` names lint, build or typecheck with no parsed runner of that kind, the result has `reason: "criterion_not_covered"` (after every existing reason), the same reason on that entry of `criteria`, and a `next_step` that names the runners read, the kinds missing, and says to run that check on its own and pipe its output. A `met` result is untouched; no verdict changes.

## Limits

These were found in review and are outside the three rules, or would need a wider rule; none is changed in code.

- `done-v2-h6/h6-c-06` has to be recorded again (one request, with a key) before `eval score --suite all` passes.
- A failing oxlint log with no exit line, or one with warnings and a criterion that does not name lint (for example "all checks pass"), now reaches Jev as facts (`errors: N`, `warnings: N`) where base had it unparsed (`unsure`). With a stub p of 0.98 these become `met`; only Jev reading the counts guards them, as for eslint and biome on base. Making parsed errors above 0 never `met` would apply to every lint parser and needs its own registration.
- A clean oxlint log is not claimed, so with no exit line it stays unparsed (`unsure`), as on base; in a log with a parsed test runner, a lint criterion that is not `met` gets `criterion_not_covered`, which is accurate there, since only the test runner's facts reach Jev.
- A clean run cut to its `Finished` line (`| tail -n 1` on oxlint 1.87, which prints `Found` first) is `unsure` (`incomplete_run`) where base gave `met`; the same cut of a run with warnings was a wrong `met` on base.
- `build_only` covers oxlint only. A build plus eslint or biome with a test criterion can still reach `met`, as on base; deriving the no-tests cap from the kinds map for every linter would widen the rule.
- R1 as registered also caps `oxlint --format=junit` on a clean run for an oxlint criterion (`failures="0" errors="0"` is problem wording that the negation does not remove); base already capped "lint is clean" there. `--format=gitlab` with warnings prints `"severity": "major"`, no warning wording, so it stays `met` on base and new, as does `{ oxlint warn; oxlint clean; } | tail -n 2`, whose window shows only the clean run.
